The problem

A demo has one path.
A system has all of them.

The tutorial version does upload → chunk → embed → answer. Every box works, and none of them says what happens when the process dies between two of them.
Changing one thing — upload returns 202 Accepted in under a second, and the work continues without the request — forces almost everything else in this system to exist.
Durable queue. Atomic claim. Lease expiry. Bounded retry. Idempotent re‑index. Tenant scoping on every read. An audit row in the same transaction.

None of that is an AI problem.

03 / 10
Trade-off 01

Postgres for the job queue. Not Redis.

Redis is faster and it is the conventional answer. I still chose the slower one.
01
A dropped job is data loss
Not a slow request. An uploaded document that silently never indexes is the worst failure this system has, because nobody finds out.
02
Postgres was already there
Already transactional, already backed up, already the source of truth. Redis would have been a second stateful system to operate for durability I had.
03
The claim is atomic by construction
FOR UPDATE SKIP LOCKED makes double-processing impossible, rather than unlikely. There is an integration test that proves it.
04
The queue is inspectable
It is a table. Debugging a stuck job at 3am is a SELECT, not a client library.

Trade-off 02

Redis caches. That's all.
A test enforces it.

A cache miss costs milliseconds. A lost queue job costs data. Those two failures should never share a system — and a note in a README does not stop the next person from mixing them.
So the boundary is a test that fails the build if any file outside an explicit allow‑list imports the cache.
It asserts on source code, not behaviour, which is an unusual thing for a test to do.

I kept it because conventions rot and tests don't. I verified it actually discriminates by introducing a deliberate violation and watching it fail, then removing it.

Incident

Six hours of silence.

The outage had nothing to do with the AI. Neither did my first fix.
Symptom
TLS completed. Request fully sent. Zero bytes back — across three attempts up to 90 seconds. Not a cold start.
Cause
A migration created a Postgres enum type, then create_table created the same type again. It could never have succeeded. The first deploy left the type behind, so every boot afterwards hit the identical wall — and migrations run before the server starts.
DuplicateObject: type "ingestion_job_status" already exists
My first fix
Also wrong. I set create_type=False on a generic enum — a parameter that only exists on the dialect-specific type and is silently ignored there. Same error, one line lower.
Real fix
The correct type, tolerant of the orphan already in production. This time I compiled the DDL and counted the statements before claiming it worked: two before, one after.
Verify, don't reason — especially about your own fix.

Evaluation

What I measure — and what I refuse to.

The right column is the harder engineering decision.
Measured
Refusal rate
The one quality signal computable with no labels at all.
Uncited answers
The shape a hallucination takes here.
Cost per answer
Real provider tokens, attributed to org and document.
Retrieval traces
The query that actually ran, with scores.
Refused
Recall & precision
Need a labelled golden set. There isn't one, so the columns don't exist — and two tests assert they never appear.
Groundedness
Same reason.
“We benchmarked the reranker”
I evaluated one and declined — but on a handful of manual queries, not a golden set. Directionally right, not rigorous. Recorded that way.

Status, stated plainly

I won't call it production‑ready.

It is production‑oriented: built with production engineering principles, on free‑tier infrastructure, with the unfinished parts named rather than smoothed over.
Built
Durable ingestion, tenant isolation, RBAC, audit trail, cost tracking, correlation IDs, hybrid retrieval, grounded citations
Partial
Worker shares the API process — the free tier has no worker service, so ingestion load and request latency are coupled. Migration trigger is written down.
Partial
Rate limits are in‑process. Correct at one worker; unenforceable at two.
Gap
No labelled golden set. Seven tuning decisions are formally blocked on it — including the similarity floor that decides between “I don't know” and a confident fabrication.
A gap you have named is not the same as one you haven't noticed.

Lessons

What the demo never teaches

01
Building the AI feature was the easy part
Reliability, cost accountability and honest uncertainty took far longer — and none of them appear in a demo video.
02
A good decision names what it rejected
A list of technologies tells you nothing. A trade-off tells you how someone thinks.
03
The best thing I shipped was something I deleted
Removing the confidence badge made the product less impressive and more trustworthy.
04
A system that admits what it doesn't know is more useful than one that sounds certain
That is an engineering property, not a UX preference.
